# Safety

This tool sends deliberately hostile-looking requests (forged tokens, downgraded PKCE, password grants, wrong redirect URIs) and it shows tokens in the clear. It is built so that, in its only mode, none of that can reach anything real. Each rule names the test that enforces it. Run them all with `npm test`.

## Why remote targets are refused

The checker does things no ordinary client does: it asks for a redirect URI that was not registered, asks for a code without PKCE, attempts a password grant, redeems a code twice. Aimed at an authorization server somebody else runs, those are probes, can trip alerts and rate limits, and (with the `target` field being free text) would turn this app into a request relay for whoever can reach its port. So the default and only mode is loopback: the five bundled stubs, or a server you run on your own machine. There is no flag to relax this in step 1. Testing a real server is a decision for the owner of that server, with a different tool.

A loopback `target` is allowed on any port. That lets you point the checker at your own local authorization server, and it also means the checker will send its fixed set of probe requests (a few `GET`s and form `POST`s to the authorization, token and PAR endpoints) to any local service you name. The request paths come from the target's own metadata or default to `/authorize`, `/token`, `/par`; nothing from the probe responses is executed or followed.

## What is not covered

- **FAPI 2.0 pack: UNVERIFIED.** It is a simplified reading of the profile written for this demo, not a conformance suite, and it has not been checked against the FAPI 2.0 text line by line. The "sender-constrained tokens" rule reads the server's metadata only; it does not exercise DPoP or mTLS. Do not use the result to say a product is or is not FAPI 2.0 compliant.
- **Nothing here is verified about specific Ping products** (PingFederate, PingOne, PingAM/AIC, PingOne Advanced Identity Cloud). The stubs imitate OAuth behaviour; they do not model any product. Whether a given product meets the BCP or FAPI 2.0 must be verified against that product before it is said to a customer.
- The BCP pack tests behaviour that can be observed from outside with a public client. It does not cover client authentication, refresh-token rotation, CORS, token lifetimes, open redirects on the authorization server's own pages, or mix-up defences beyond the `iss` parameter.
- The flow catalog is a simulation. Keys and certificates are generated per run; no TLS is performed; the attack outcomes are computed by small in-memory checks (hash compare, signature verify) to show why a protection works, not by running the protocols.
- The stub resource server accepts `ES256` tokens only and has no replay (`jti`) cache or DPoP/mTLS proof validation; `cnf` is decoded and explained, not enforced.
- The user-vs-agent case answers 403 `insufficient_scope`: RFC 6750 has no error code for "wrong kind of token", so that is a demo policy choice.
- **Cookie headers are not checked and never read.** Cookies are scoped by host, not port, so other local apps' cookies reach this server; it does not look at them and does not send any.
- Redaction of tokens is not attempted: tokens are shown on purpose, in the response to the request that supplied or minted them.
